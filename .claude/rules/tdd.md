# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없거나 다루지 않는 부분에만 적용한다.

## 적용 기준

### TDD를 반드시 적용하는 대상

- 비즈니스 로직
- API (엔드포인트, 요청/응답 처리, 외부 서비스 호출 래퍼)
- 유틸 함수
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성한다)

### TDD가 불필요한 대상

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업, 스타일링)
- SQL

판단이 애매하면 **적용하는 쪽**으로 결정한다.

## RED-GREEN-REFACTOR

### 1. RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트 이름은 기대하는 동작을 설명한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 테스트가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 오타, import 오류, 설정 오류로 실패했다면 RED가 아니다. 먼저 고친 뒤 다시 실행한다.
- 작성하자마자 통과한 테스트는 아무것도 증명하지 못한다. 테스트를 고친다.

### 2. GREEN: 최소한의 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 분기, 옵션, 추상화는 쓰지 않는다.
- **신규 테스트와 기존 테스트 모두** 실행해서 전부 통과하는지 확인한다.

### 3. REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- 매 변경 후 테스트를 실행해 **green을 유지**한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 4. 반복

다음 동작에 대한 **RED로 돌아간다.** 모든 동작이 끝날 때까지 반복한다.

## 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 삭제하고 RED부터 다시 시작**한다.
- **"참고용"으로 남기는 것도 금지**다. 주석 처리, 별도 파일 보관, 복사해 두기 모두 포함한다. 남겨 두면 그 코드를 보고 테스트를 맞추게 된다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드가 가장 먼저 깨지고, 테스트 작성은 30초면 끝난다. 단순하다면 테스트도 단순하다. |
| "나중에 테스트 추가하겠다" | 나중은 오지 않는다. 코드를 먼저 쓰고 만든 테스트는 구현을 따라가므로 버그를 못 잡는다. |
| "시간이 없다" | 테스트 없는 코드는 디버깅과 회귀 수정으로 더 많은 시간을 쓰게 한다. 급할수록 TDD가 빠르다. |
| "삭제하면 낭비다" | 이미 쓴 시간은 매몰 비용이다. 검증되지 않은 코드를 유지하는 것이 더 큰 비용이다. 다시 쓰는 건 빠르다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 TDD 대상에서 빠지는 게 아니라 애초에 커밋하지 않으면 된다. |
