# commit

변경사항을 읽고, 의미 단위로 나누고, 한국어 커밋 메시지를 작성해 **사용자에게 따로 묻지 않고 바로 커밋한다.**
사용자가 커밋을 요청한 것 자체가 승인이므로 확인 질문으로 흐름을 끊지 않는다. 대신 무엇을 커밋했는지는 끝에 반드시 보고한다.

## 절차

### 1. 변경사항 분석

먼저 저장소 상태를 파악한다.

```bash
git status --short
git diff            # 아직 stage되지 않은 변경
git diff --staged   # 이미 stage된 변경
git log --oneline -10   # 이 저장소의 기존 메시지 스타일 확인
```

- git 저장소가 아니면(`git status`가 실패하면) 커밋할 수 없으므로 그 사실을 알리고 멈춘다. 임의로 `git init` 하지 않는다.
- untracked 파일은 `git diff`에 나오지 않으므로 `git status` 목록을 보고 필요하면 내용을 직접 읽는다.
- `.env`, 키·토큰이 들어간 파일, `node_modules`, 빌드 산출물(`dist` 등)처럼 커밋하면 안 되는 파일이 보이면 제외하고 사용자에게 알린다. 한 번 커밋된 비밀 값은 히스토리에서 지우기 어렵다.
- 사용자가 이미 stage해 둔 내용이 있다면 그 의도를 존중해 stage된 변경을 우선 한 단위로 본다.

### 2. 논리적 단위로 분류

"하나의 커밋 = 하나의 이유"가 되도록 나눈다. 나중에 `git log`나 `git revert`로 한 가지 이유만 골라 볼 수 있게 하기 위해서다.

- 서로 다른 목적의 변경(기능 추가 + 버그 수정, 코드 변경 + 설정 변경 등)은 분리한다.
- 같은 목적을 이루기 위한 파일들(컴포넌트 + 스타일 + 테스트)은 한 커밋으로 묶는다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 `git add -p`로 hunk 단위로 나눌 수 있지만, 대화형 모드(`-i`)는 이 환경에서 지원되지 않으므로 나누기 어렵다면 한 커밋으로 묶고 그 이유를 설명한다.
- 변경이 작고 목적이 하나면 억지로 쪼개지 않는다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>

<필요할 때만: 왜 바꿨는지, 눈여겨볼 점>
```

| type | 쓰임 |
|------|------|
| `feat` | 사용자에게 보이는 새 기능 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 같고 구조만 개선 |
| `chore` | 설정, 의존성, 빌드, 문서, 스타일 등 기타 |

- 요약은 한 줄, 가능하면 50자 안팎으로 쓰고 마침표는 붙이지 않는다. 무엇이 달라졌는지 읽는 사람이 바로 알 수 있게 쓴다.
- 파일 이름을 나열하기보다 "무엇을/왜"를 쓴다. 파일 목록은 diff가 이미 보여준다.
- 본문은 요약만으로 부족할 때만 쓴다. 이유가 자명한 변경에 본문을 붙이면 오히려 읽기 부담만 는다.
- 위 네 가지로 딱 맞지 않으면(예: 테스트 추가, 성능 개선) 가장 가까운 type을 쓰고, 저장소의 기존 로그가 다른 type(`test`, `docs`, `style`, `perf`)을 쓰고 있으면 그 관례를 따른다.
- 이 세션의 system-reminder에 커밋 attribution 지침(예: `Co-Authored-By`)이 있으면 메시지 맨 끝에 그대로 붙인다. 지침이 없으면 붙이지 않는다.

예시:

```
feat: 결과 창에 폴더 탭 스타일 탭 추가
```

```
fix: API 키가 비어 있을 때 서버 키를 쓰지 않던 문제 수정

hasEnvKey 확인 전에 early return 하던 순서를 바로잡았다.
```

```
chore: 레트로 테마용 Galmuri 폰트 CDN 추가
```

### 4. 커밋 실행

승인 질문 없이 분류한 단위마다 필요한 파일만 이름으로 stage하고 커밋한다.
사용자가 "하나로 커밋해"처럼 방식을 지정했다면 그대로 따른다. `git add -A`나 `git add .`는 제외하기로 한 파일까지 끌어들일 수 있어 쓰지 않는다.

```bash
git add <파일...>
git commit -m "$(cat <<'EOF'
feat: 요약

본문(있다면)
EOF
)"
```

- 여러 줄 메시지는 heredoc으로 넘겨 따옴표와 줄바꿈이 깨지지 않게 한다.
- pre-commit hook이 실패하면 `--no-verify`로 우회하지 말고 원인을 고쳐서 **새로 커밋**한다. 실패한 시도에서는 커밋이 만들어지지 않았으므로 `--amend`를 쓰면 이전 커밋을 덮어쓰게 된다.
- 이미 만들어진 커밋을 수정(`--amend`)하거나 `reset`하는 것은 사용자가 요청했을 때만 한다.
- 모든 커밋이 끝나면 `git log --oneline -n <커밋 수>`와 `git status --short`로 결과를 확인하고, 만든 커밋 목록(해시, 메시지)과 남은 변경사항을 알려준다. 묻지 않고 커밋하는 만큼 이 보고가 사용자가 결과를 확인하고 필요하면 되돌릴 수 있는 유일한 지점이다.
- 제외한 파일(비밀 값, 빌드 산출물 등)이 있으면 보고에 이유와 함께 적는다.
- `git push`는 하지 않는다. 사용자가 따로 요청할 때만 한다.
